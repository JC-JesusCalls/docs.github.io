CMS User Manual

Every content type and field used by the Homepage, Humanitarian Page and University Page — whether it's required, its default value, allowed values, and what it changes on the live site. Required / Default values are taken directly from the Strapi schema files, so they're exact, not approximations.

⚠️ Draft changes never appear on the site. All types use Draft & Publish — always Save → Publish. All types are localized (en / ta / hi / ml / te); check the locale dropdown before editing. A \n inside a text label creates a line break on the website.

1.15 Responsive Images — upload sizes by breakpoint

The frontend renders three widths: Desktop (≥1024px), Tablet (768–1023px) and Mobile (<768px). Not every section gives you a separate upload slot for all three — check the field list for the section you're editing before you assume tablet/mobile get their own image. Where a breakpoint has no dedicated field, that viewport reuses the desktop image (scaled down by the browser), so pick a crop that still reads well small.

Breakpoint Recommended upload width Aspect ratio Notes
Desktop 1600–1920px wide 21/9 or 16/9 for hero banners; 4/3 or 1/1 for content photos Export @2x for retina screens; keep under ~500KB (compress/WebP) so hero sections stay fast
Tablet 1024–1200px wide Same ratio as desktop unless the design crops tighter Re-crop rather than just shrinking the desktop image if faces/text sit near the edges
Mobile 750–900px wide 4/5 or 1/1 — portrait crops read better on phones than wide 21/9 hero images This is the field most often left empty by mistake — always preview on an actual phone width before publishing

Field-name patterns you'll see across the CMS — Strapi doesn't enforce one convention, so check which pattern the section you're in actually uses:

Pattern Breakpoints covered Where it's used
bgImage / tab_bgImage / mobile_bgImage Desktop, Tablet, Mobile (full 3-tier) Home Hero Banner slides (Part 4)
desktop_image / tab_image / mobile_image Desktop, Tablet, Mobile (full 3-tier) University Banner (Part 5)
background / tab_image / mobile_image Desktop, Tablet, Mobile (full 3-tier) Bible Banner (Part 4, Bible page)
image / mobileImage Desktop only, plus one Mobile override — no tablet slot Humanitarian Banner Section (Part 3, Humanitarian page). Tablet viewports fall back to image
media / plain image Single image, reused at every breakpoint — no responsive override at all Donate "Project of the Month" slides, University Institution/Story cards, Humanitarian Programs & Services and Stories of Transformation cards
Uploading a set of device images? Go to Media Library → Upload, add the Desktop/Tablet/Mobile files as separate assets first (name them so you can tell them apart, e.g. humanitarian-hero-desktop.jpg, …-tablet.jpg, …-mobile.jpg), then open the content entry and assign each file to its matching field. Sections with only a single image field (last row above) don't need this — one upload covers every device, so choose a crop that still works cropped tighter on a phone.

1.16 Language-specific font sizes

Text, Description, Tagline and Button components (1.1, 1.2, 1.13, 1.3) all carry three size fields — desktopFontSize, tabFontSize and mobileFontSize — set in pixels. These aren't language-aware by themselves; they become language-specific because the pages using them are localized (pluginOptions.i18n.localized: true). Every locale (English, Tamil, Hindi, Malayalam, Telugu) is a fully separate content entry, so each locale's copy of a Text/Description component keeps its own desktopFontSize / tabFontSize / mobileFontSize independent of the others.

Step What to do
1 Open the entry (e.g. Home Page → Hero Banner) and use the locale selector in the top-right of the content editor to switch to the language you want to adjust
2 Expand the Text/Description field and set desktopFontSize / tabFontSize / mobileFontSize for that locale only — this does not change any other language's entry
3 Repeat per locale. Scripts that run visually larger at the same pixel size (e.g. Tamil, Malayalam) typically read correctly a couple of sizes down from the English value
Example. English title set to desktopFontSize: 14 reads comfortably. Switch the locale selector to Tamil and set the same field to desktopFontSize: 12 — English keeps 14 on desktop, Tamil renders at 12 on desktop, and each language still has its own independent tablet/mobile sizes on top of that. If a locale is left blank, the component's schema default applies (e.g. Text/Description/Tagline default mobileFontSize to 12).

Troubleshooting

Can't save? A required field is empty — check the tables above.
Change not on the site? You forgot Publish, edited the wrong locale, or the cache hasn't refreshed (hard refresh: Ctrl+Shift+R).
Blessing plan not showing? isFeatured is false, or isActive is false, or maxPlansToShow cap reached.
Event card not showing? eventSource must be manual and the card attached in eventCards; only the first maxEventsShown (max 3) appear.

Troubleshooting — Donate Page

A section shows blank on the live page? Each of the 5 sections is fetched independently by its own url — check that specific section's own single type is Published, not just donate-page.
Page not found / slug mismatch? Check pageBase.slug for a stray leading or trailing space.
Donation form not appearing in the hero? The attached Contact Form entry under donation_forms / popup_contact_form must itself be Published.
New impact/membership/ticker item not showing? Confirm isActive = true on the item, and check maxItems on the parent section hasn't already been filled by lower-order entries.
Bible Page — Overview

Content Types

The Bible page is a single content type — unlike Donate, Humanitarian and University, it has no companion section APIs and no page-base/sectionOrder. Everything lives in one dynamic zone. Localized (en / ta / hi / ml / te), Draft & Publish enabled.

# Content Type Kind API Controls
1 Bible Single /bible Page title, slug, SEO + sections[] dynamic zone (banner, CTA banner, reader UI labels)
⚠️ This content type has no public read permission configured. api::bible.bible does not appear in src/utils/ensure-public-permissions.js at all — the Public role has no find access, so GET /api/bible currently 403s for anonymous requests even though jc-web-app's Bible page mapper (bible-page.mapper.ts) depends on it. This is the same class of gap previously found on the Humanitarian domain — add { uid: "api::bible.bible", actions: ["find"] } to the allowlist to fix it.
Scripture text is not stored here. None of the fields below hold actual verse/chapter content — bible-content is just UI copy (button labels, tab labels, placeholders). The actual Bible text, books and chapters are served separately by jc-core-backend's Bible module, which proxies the Digital Bible Platform API. This CMS single type only controls the static wrapper around that reader (banner + CTA + interface labels).
Part 1

Bible Page

/bible

Single type. Page identity, SEO and the ordered dynamic zone that composes the page — no page-base/sectionOrder wrapper like the other pages in this manual.

Field Required Default Notes

seo No — SEO (1.11)
sections[] No — Dynamic zone — mix any of Magazine CTA Banner, Bible Banner, Bible Content, in any order, detailed in Parts 2–4 below
No isPublished flag. Unlike Donate, Humanitarian and University (which gate visibility on pageBase.isPublished), the Bible page has no such field — publishing the entry itself (Strapi's normal Draft & Publish workflow) is what controls visibility.

Task Where Watch out for
Change the Bible page title/SEO Bible → pageTitle / slug / seo No sectionOrder here — order is controlled purely by the position of blocks inside sections[]

Troubleshooting — Bible Page

Page returns 403 / frontend can't load it at all? Check Settings → Users & Permissions → Public role — api::bible.bible is currently missing from the public-read allowlist (see the Overview callout above); this is a known, unresolved gap as of this manual's last update.
Verses/chapters missing or wrong? Not a CMS issue — that content is served by jc-core-backend's Bible module, not this content type.
A block added to sections[] isn't rendering? Confirm the entry itself is Published — dynamic zone blocks inherit the parent Bible entry's publish state, they have no publish flag of their own.
